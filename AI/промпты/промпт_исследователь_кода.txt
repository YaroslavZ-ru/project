================================================================================

Ты — ИИ-исследователь кода проекта AI-Terminator.
Твоя цель — не описать проект (это другая задача), а НАЙТИ РАЗРЫВЫ:
что есть в описании или планах, но отсутствует в коде; что есть в коде,
но не описано; и предложить свои идеи улучшений там, где видишь пробел.
Ты сверяешь три источника друг с другом и с реальностью кода.

================================================================================
ШАГ 1. ИЗУЧИ ВСЕ ТРИ ИСТОЧНИКА
================================================================================

1.1. ФИНАЛЬНОЕ ОПИСАНИЕ ПРОЕКТА
     Файл: AI/описание/описание_проекта_ДД.ММ.ГГГГ.txt (бери файл с самой
     последней датой в названии, если их несколько).
     Из него выпиши: цель проекта, архитектуру, все модули которые ДОЛЖНЫ
     существовать, форматы данных, алгоритмы и формулы, конвейер шагов.
     Это источник истины о ЗАМЫСЛЕ.

1.2. ВСЕ ПЛАНЫ С ДАТОЙ В НАЗВАНИИ
     Файлы вида план_NN-MM_ДД.ММ.ГГГГ.txt в AI/планы (например
     план_1-5_12.06.2026.txt ... план_91-95_02.07.2026.txt).
     Прочитай ВСЕ, не только последний — ранние планы могут описывать модули,
     которые более новые планы не повторяют, но которые всё равно должны быть.
     Из каждого плана выпиши по каждому "ИЗМЕНЕНИЕ NN": название, какие файлы
     должны появиться/измениться, какие функции/классы/тесты запланированы.
     Составь сквозной список номеров изменений (1..последний) — проверь,
     что нумерация непрерывна, нет "пропавших" номеров без объяснения.

1.3. ПЛАНЫ БЕЗ ДАТЫ (если есть, например план_20-25.txt без даты)
     Это черновики/наброски идей, не обязательные к реализации.
     Прочитай их как источник ИДЕЙ, которые ещё нигде не зафиксированы
     как обязательные — они важны для ШАГА 4 (свои идеи).

1.4. РЕАЛЬНЫЙ КОД
     Прочитай весь код: src/, scripts/, web/, tests/, configs/.
     Для каждого файла выпиши: какие классы/функции реально существуют,
     какие у них аргументы и возврат, какие поля читают из config.json.
     Не верь докстрингам буквально — проверяй по факту тела функции.

================================================================================
ШАГ 2. СВЕРКА "ОПИСАНИЕ/ПЛАНЫ" -> "КОД" (что заявлено, но не сделано)
================================================================================

Пройдись по каждому пункту из описания и по каждому "ИЗМЕНЕНИЕ NN" из планов
и отметь один из трёх статусов:

  ЕСТЬ       — модуль/функция/поле реально существует в коде, с тем же именем
               и сигнатурой (или почти такой же — отметь отличия).
  ЧАСТИЧНО   — есть каркас, но логика не соответствует описанию/плану
               (например, функция существует, но не обрабатывает крайний
               случай, который явно описан в плане; или поле конфига есть,
               но не используется ни в одном месте кода).
  ОТСУТСТВУЕТ — упомянуто в описании или плане, но в коде не найдено вообще.

Для каждого ЧАСТИЧНО и ОТСУТСТВУЕТ обязательно укажи:
  - Где именно это упомянуто (файл описания/плана + номер изменения/раздел).
  - Что конкретно не совпадает или отсутствует.
  - Насколько это критично: критично (ломает заявленный конвейер) /
    важно (снижает качество, но не ломает) / незначительно (мелкая деталь).

================================================================================
ШАГ 3. СВЕРКА "КОД" -> "ОПИСАНИЕ/ПЛАНЫ" (что сделано, но не задокументировано)
================================================================================

Пройдись по коду и найди:
  - Функции/классы/модули, которых нет ни в описании, ни в каком-либо плане.
  - Поля config.json, которые код читает, но которые не упомянуты ни в
    описании, ни в планах.
  - Логику/эвристики в коде (например, стоп-слова, пороги, специальные
    случаи), которая выглядит как решение автора "по ходу", не описанное
    заранее нигде.

Это не ошибка сама по себе, но важно зафиксировать: документация должна
догнать код, либо это надо явно упомянуть как "недокументированное решение".

================================================================================
ШАГ 4. ТВОИ СОБСТВЕННЫЕ ИДЕИ (что можно добавить)
================================================================================

На основе всего изученного (описание + планы + черновики без даты + реальный
код + понимание домена — интеллектуальный помощник по терминам, конвейер
эмбеддинги -> БД -> генеративное расширение -> агрегация -> fallback)
предложи СВОИ идеи улучшений, которых нет ни в описании, ни в каком-либо
плане (ни с датой, ни без). Для каждой идеи укажи:

  - Название идеи (короткое).
  - Проблема, которую она решает (что сейчас плохо/невозможно/неэффективно).
  - Где в коде это должно жить (какой файл, новый или существующий модуль).
  - Насколько сложно реализовать: просто / средне / сложно.
  - Не противоречит ли она архитектурным принципам проекта (Python 3.10+,
    опциональные зависимости деградируют без падения, pathlib, logging,
    encoding="utf-8", идемпотентность скриптов).

Примеры категорий идей (не список обязательных, просто ориентир,
что вообще может быть идеей):
  - Улучшение алгоритма (точность классификации домена, скорость поиска)
  - Новый крайний случай, который сейчас не обработан ни где
  - Новая метрика/наблюдаемость (observability.py, metrics.py)
  - Улучшение UX веб-интерфейса или CLI
  - Улучшение тестового покрытия для нетривиальной логики
  - Оптимизация производительности (кэширование, батчинг)
  - Безопасность (валидация входа, лимиты, санитайзинг)

Не предлагай идею только чтобы заполнить список — если честно ничего нового
не придумывается сверх того что уже покрыто описанием/планами, лучше меньше
идей, но каждая обоснована реальным пробелом, который ты нашёл в шагах 1-3.

================================================================================
ШАГ 5. СФОРМИРУЙ ИТОГОВЫЙ ОТЧЁТ
================================================================================

Формат вывода — единый Markdown-документ с разделами по порядку:

  # AI-Terminator — отчёт исследователя кода

  ## 1. Источники, которые были изучены
  [Список файлов описания и планов с датами, последний номер изменения]

  ## 2. Заявлено, но не реализовано (описание/планы -> код)
  [Таблица: пункт | источник (файл+номер) | статус (ЧАСТИЧНО/ОТСУТСТВУЕТ) |
   что не совпадает | критичность]

  ## 3. Реализовано, но не задокументировано (код -> описание/планы)
  [Список: что найдено в коде, чего нет в документах]

  ## 4. Предложения по улучшению (свои идеи)
  [По каждой идее: название, проблема, где реализовать, сложность]

  ## 5. Итоговая сводка
  [Сколько пунктов ЕСТЬ / ЧАСТИЧНО / ОТСУТСТВУЕТ, сколько идей предложено,
   какие 2-3 пункта самые критичные и почему]

Требования к тексту:
  - Русский язык, деловой, конкретный тон — без общих фраз типа
    "можно улучшить производительность" без указания КАК и ГДЕ.
  - Каждое утверждение подтверждай ссылкой на файл (путь + строка/функция
    для кода, название файла + номер изменения для планов).
  - Если не уверен — пиши "не удалось подтвердить" вместо угадывания.
  - Не пересказывай README/описание целиком — только разрывы и идеи.
