ОБЩИЕ ПРИНЦИПЫ ДЛЯ ВСЕГО БЛОКА 55-60
================================================================================

1. Ничего не ломать: существующая функциональность остаётся рабочей.
2. Новые возможности вводятся через опциональные флаги конфигурации.
3. Все пути строятся через pathlib.Path; sys.path.insert — только внутри
   if __name__ == "__main__".
4. Логирование остаётся структурированным и пригодным для централизованного
   сбора и анализа.
5. Type hints, docstrings Google-style и статическая типизация everywhere.
6. Все новые скрипты идемпотентны: повторный запуск не ломает данные.
7. Опциональные зависимости оборачиваются в try/except ImportError.
8. Сценарии ошибок документируются и проверяются в тестах.
9. Весь новый API и скрипты должны поддерживать режимы debug/verbose.
10. Документация обновляется параллельно с кодом, чтобы не было рассинхронизации.

ИЗМЕНЕНИЕ 55: Обзорная наблюдаемость и трассировка запросов
================================================================================

КОНТЕКСТ И ЗАДАЧА
-----------------
Сейчас API возвращает результат запроса и считает базовые метрики.
Для боевого использования нужно добавить прозрачную трассировку, которая
покажет, как запрос прошёл через этапы предобработки, векторизации,
поиска и агрегации, а также сохранить уникальный идентификатор запроса
для корреляции логов и обратной связи.

ПОЧЕМУ ЭТО ВАЖНО
----------------
  - позволяет отлаживать медленные или неисправные запросы;
  - упрощает расследование ошибок в условиях распределённой системы;
  - даёт возможность связать лог события с конкретным `request_id`;
  - является базой для улучшения SLA и оперативного реагирования.

ТЕЧЕНИЕ ЗАДАЧИ
--------------
1. Создать модуль `src/observability.py`.
2. Расширить `main.py` и `src/api.py` для передачи `request_id`.
3. Уточнить формат логов и метрик.
4. Обновить тесты и документацию.

ПОДРОБНАЯ РЕАЛИЗАЦИЯ
-------------------

  src/observability.py
    - импорт: datetime, logging, uuid, typing.
    - класс RequestStage:
        * name: str
        * duration_s: float
        * details: dict[str, typing.Any] | None
        * timestamp: str

    - класс RequestTraceContext:
        * request_id: str
        * started_at: float
        * stages: list[RequestStage]
        * metadata: dict[str, typing.Any]
        * log_level: str = "INFO"

    - методы RequestTraceContext:
        * add_stage(name: str, duration_s: float, details: dict | None = None) -> None
        * get_summary() -> dict[str, typing.Any]
        * to_dict() -> dict[str, typing.Any]
        * elapsed() -> float

    - функции модуля:
        * generate_request_id() -> str
          - использовать uuid.uuid4().hex
        * format_log_record(record: dict[str, typing.Any]) -> str
          - возвращает сериализованный JSON для stdout/файлов.
        * get_default_trace_context(request_id: str | None = None) -> RequestTraceContext

    - дополнительные утилиты:
        * is_json_serializable(value: typing.Any) -> bool
          - гарантирует, что поля логов переводятся в JSON.

  src/api.py
    - добавить опциональный header `X-Request-Id`.
    - при обработке POST /v1/query:
        * request_id = request.headers.get("X-Request-Id") или generate_request_id().
        * context = RequestTraceContext(request_id=request_id)
        * передать context в `_api_run_pipeline`.
    - логировать начало и конец каждого HTTP запроса:
        logger.info({"event": "request.start", "request_id": request_id, "path": str(request.url)})
        logger.info({"event": "request.complete", "request_id": request_id, "status": status_code, "duration_s": total_time})
    - при исключении возвращать JSON с `request_id` и `detail`.
    - добавить поле `request_id` в Pydantic-модель `QueryResponse`.

  main.py

    - использовать `RequestTraceContext` для фиксации этапов:

    - передавать `trace_context` в результат:
        result["request_id"] = request_id
        result["trace"] = trace_context.to_dict() если debug=True или если request_id задан.
    - при каждом основном шаге использовать `time.monotonic()` и `add_stage(...)`.

  src/metrics.py

    - в методе `record_request`: принимать `endpoint: str` и `status: str`.

    - если `use_metrics=True`, экспортировать метрики для каждого этапа:

  docs/api.md
    - зафиксировать поведение `X-Request-Id`.

ИЗМЕНЕНИЕ 56: Администрирование KB и резервное копирование данных
================================================================================

КОНТЕКСТ И ЗАДАЧА
-----------------
База знаний является критическим хранилищем проекта. Уже есть парные функции
по обновлению и инициализации, но нет удобных инструментов для резервного
копирования, восстановления и диагностики целостности данных.

ПОЧЕМУ ЭТО ВАЖНО
----------------
  - обеспечивает возможность отката после ошибочного обновления;
  - позволяет безопасно переносить БД между средами;
  - делает проект доступным для администраторов без ручного копирования файлов;
  - упрощает контроль целостности и подготовку к инцидентам.

ЦЕЛИ
-----
  - автоматизировать создание резервных копий SQLite.
  - добавить проверку структуры БД и данных.
  - предоставить безопасный сценарий восстановления из резервной копии.
  - расширить документацию и конфиг.

ДЕТАЛИ РЕАЛИЗАЦИИ
-------------------

  scripts/backup_db.py
    - импорт: argparse, logging, shutil, sys, time.
    - определить `DEFAULT_BACKUP_DIR = Path("backups")`.
    - `main()` принимает опции:
        --config          путь к configs/config.json
        --output          путь к целевой папке (по умолчанию backup_dir из конфига)
        --force           перезаписать файл, если уже существует.
    - шаги:
        1. загрузить конфиг `Config.from_json(config_path)`.
        2. построить `backup_dir = Path(output) or Path(cfg.backup_dir)`.
        3. создать папку `backup_dir` с `mkdir(parents=True, exist_ok=True)`.
        4. проверить, что файл `cfg.db_path` существует.
        5. сформировать имя `knowledge_base_%Y%m%d_%H%M%S.db`.
        6. скопировать файл через `shutil.copy2`.
        7. вывести `OK: backup created at ...`.
    - возвращать exit 0 при успехе, 1 при ошибке.
    - логировать WARNING при `backup_dir` в сети или на недоступном носителе.

  scripts/restore_db.py
    - импорт: argparse, logging, shutil, sqlite3, sys.
    - `main()` принимает опции:
        --source          путь к резервной копии SQLite
        --config          путь к configs/config.json
        --force           выполнять восстановление без запроса подтверждения.
    - шаги:
        1. проверить, что `source` существует.
        2. открыть `sqlite3.connect(source)`.
        3. выполнить `SELECT name FROM sqlite_master WHERE type='table'`.
        4. убедиться, что таблица `concepts` присутствует.
        5. закрыть соединение.
        6. скопировать файл в `cfg.db_path` через `shutil.copy2`.
        7. вывести `OK: database restored to ...`.
    - если `cfg.enable_admin_tools` false — выводить WARN и завершать.

  src/admin.py
    - импорт: sqlite3, logging, pathlib.Path, typing.
    - `validate_kb_integrity(db_path: Path) -> dict[str, typing.Any]`:
        * проверяет доступность файла.
        * проверяет наличие таблиц `concepts`, `parameters`, `relations`, `metadata`.
        * проверяет индексы `idx_concepts_domain`, `idx_parameters_concept_id`, `idx_relations_source`, `idx_relations_target`.
        * проверяет schema_version в metadata.
        * возвращает словарь с полями `status`, `details`, `errors`, `warnings`.
    - `list_unmapped_relations(db_path: Path) -> list[dict[str, typing.Any]]`:
        * ищет концепты, у которых нет ни исходящих, ни входящих отношений.
        * возвращает список словарей `{ concept_id, term, domain }`.
    - `refresh_faiss_index(kb: KnowledgeBase) -> None`:
        * вызывает `kb.update_all_embeddings()` и `kb._build_faiss_index()` если `use_faiss`.
        * логирует прогресс.
    - `backup_database(db_path: Path, backup_dir: Path) -> Path`:
        * малая вспомогательная функция для копирования файла.

  src/config.py
    - добавить поля:
        * `backup_dir: str = "backups"`
        * `enable_admin_tools: bool = False`
    - проверка `_validate`:
        * `backup_dir` должен быть строкой и не пустым.
        * если `enable_admin_tools` не bool — `ValueError`.
    - `Config.from_json` должна корректно читать новые поля.

  docs/configuration.md
    - описать `backup_dir` и `enable_admin_tools`.
    - пояснить использование `scripts/backup_db.py` и `scripts/restore_db.py`.
    - добавить примеры команд.

  README.md
    - добавить раздел `Администрирование базы знаний`.
    - описать шаги резервного копирования и восстановления.
    - предупредить об обязательном выключении сервиса перед `restore`.

  .github/workflows/ci.yml
    - в `ci` добавить шаг `Check config secrets`:
        * проверять, что `configs/config.json` не содержит `API_KEY`.
        * проверять, что `configs/config.json` не содержит секретных строк.

ИЗМЕНЕНИЕ 58: Производительность, профилирование и масштабирование
================================================================================

КОНТЕКСТ И ЗАДАЧА

Проект уже содержит базовые метрики и API, но нет регрессионного сценария,
позволяющего сравнивать производительность с базовой линией. Также не хватает
детального замера длительности этапов пайплайна.

ПОЧЕМУ ЭТО ВАЖНО
----------------
  - позволяет определить узкие места в реальном коде;
  - поддерживает принятие решений при оптимизации;
  - даёт команды возможность контролировать изменения производительности;
  - помогает обнаруживать деградации после изменения модели или данных.

ЦЕЛИ
-----
  - собрать промежуточные метрики по этапам.
  - добавить сценарий регрессии производительности.
  - подготовить коллекцию данных для анализа.
  - улучшить потенциальный FAISS-воркфлоу.

ДЕТАЛИ РЕАЛИЗАЦИИ
-------------------

  scripts/regression.py
    - импорт: argparse, json, logging, statistics, sys, time.
    - `main()` принимает:
        * `--config` путь к JSON-конфигу;
        * `--dataset` путь к `data/eval_dataset.json`;
        * `--output` путь к JSON-отчёту;
        * `--runs` количество повторений на каждом примере.
    - процесс:
